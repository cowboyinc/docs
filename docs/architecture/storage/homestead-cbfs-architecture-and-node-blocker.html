Homestead already stores its workspace in CBFS.

This document records the shipped file-based service, shows each user operation, and captures the Node/RAS import failure that motivated the native shard-index branch. It proposes no Homestead or CBFS storage rewrite.

Decision

Keep the shipped Homestead service registry and CBFS layout. Do not replace it with one metadata file per page. Do not add PoR, shard proofs, or storage-index logic to Homestead. Fix the volume-growth failure below the CBFS API in Node/RAS.

Current durable layout

The persistent collaboration service is the single writer for its workspace volume. CBFS stores immutable registry history and room content; SQLite is rebuilt from that history.

Registry segments are append-only. A mutation publishes a new immutable segment and advances the small head; it does not rewrite a global page tree.

Registry record

Fields that must stay together

  • stable page ID, parent, title, icon, order, and trash/delete state;
  • revision used for compare-and-swap and route expectations;
  • ready routing assignment: stream ID, metadata version, and four authenticated lanes;
  • grants, public links, and effective page policy;
  • policy and membership generations needed for fresh authorization;
  • operation result and idempotency receipt for confirmed retries.

These records are recovered from CBFS journal segments and signed checkpoints into registry.sqlite.

The import blocker that motivated the Node change

Every service publication above was already an ordinary CBFS commit. The observed import failed after that boundary because the previous Node/RAS path rewrote a complete live-shard vector into one actor-storage value. The native shard-index branch removes that path.

Homestead and CBFS

No new page files, CBFS index, proof payload, or application-level shard structure. Existing service operations and immutable CBFS formats remain intact.

Branch fix

Node consensus storage

Open Node #1724 removes the one-value shard-inventory ceiling and the full-value rewrite from the RAS commit path. The manifest layout and write-relayer request schema remain unchanged. CBFS #265 has merged to devnet with a typed paged recovery reader and exact removal roots; its deployment must be coordinated with a Node build containing #1724.

PoR remains a Node responsibility. Node pins the selected native row when it issues a challenge and verifies the response against that snapshot. Homestead does not construct or transport PoR proofs.

Node fix: a native keyed shard index

Use the ordered, merkleized QMDB state that Node already commits in BlockchainStorage::state_root. The index lives in domain-separated SystemState rows, not Storage Manager actor KV. Each value is small, and every manifest commit touches O(delta) inventory rows: the named rows plus the moved tail row for a non-tail removal.

Primary row

Find one live shard

Logical key "ras/inventory/v1/primary\0" || volume || shard || index → chunk root, ciphertext size, ordinal, and the event sequence at which this incarnation was added.

Ordinal row

Select and enumerate

Logical key "ras/inventory/v1/ordinal\0" || volume || ordinal_be → shard ID and shard index. The production store maps both logical-key forms through StateKey::system_state, whose physical key is 0x0A || Keccak256(logical_key) || zero padding.

Volume header

Bound the live set

StorageCommitment.live_shard_count is the next append ordinal and the O(1) count used by PoR sampling and paged recovery reads.

One explicit limit replaces the accidental JSON limit.MAX_LIVE_SHARDS_PER_VOLUME = 1,048,576. That supports roughly 174,000 six-shard files while bounding consensus-state growth and ordinal arithmetic. The current Homestead archive needs at most the low thousands, not millions. MAX_COMMIT_FINALIZE_SHARDS = 65,536 still caps the combined added and removed references in one commit finalization.
A

Apply one manifest commit in O(delta)

No full inventory load, sort, hash, or rewrite
ValidatePoint-read named keysReject missing removals, duplicate additions, and removals whose root or size differs from the stored primary row. Every removal carries the real nonzero chunk root. Reject invalid additions and a count above the hard limit before changing state.
RemoveSwap-delete ordinalsMove the last ordinal into a removed slot, update that shard's primary row, then delete the old last row and removed primary row.
AddAppend ordinalsWrite one primary row and one ordinal row per new shard, stamp the primary with this commit's event sequence, and advance live_shard_count.
CommitUse the existing transaction boundaryThe inventory rows, volume commitment, event chunks, relay accounting, and manifest root succeed or roll back together.

Cost: O(added + removed) inventory reads and writes. Access-weight table version 15 reserves 2 point reads + 2 writes per addition, 4 + 4 for a worst-case non-tail removal, 1 + 1 per event page, and one fixed native revision read + write per commit, where pages = ceil(added / 512) + ceil(removed / 512); direct and staged-finalize paths use the same split rows. State is authenticated by the existing global Node state root. Global QMDB finalization is benchmarked separately rather than assumed to be O(delta).

Storage API

Narrow namespace, typed callers

StateReader/StateWriter expose ras_inventory_get, ras_inventory_put, and ras_inventory_delete. The production store accepts only logical keys under ras/inventory/v1/ before mapping them into SystemState; execution builds and decodes primary and ordinal rows through typed helpers. Execution never receives arbitrary SystemState access.

Atomicity proof

Test the actual overlay

A failing finalize must roll back primary rows, ordinal rows, live_shard_count, the volume commitment, and event/accounting writes together. A second test exercises speculative commit/revert so read-your-writes and state-root behavior are demonstrated, not inferred.

CIP-9 §5.6 and §11.1 amendment.Remove StorageCommitment.shard_root and its [0;32] “no anchor, do not slash” sentinel. Live membership and rank are committed by the native QMDB primary/ordinal rows plus live_shard_count under the global state root. Version 2 defines rank by dense ordinal (deterministic commit order plus swap-delete), replacing sorted-key rank while preserving uniform selection. Consensus selects a live row and pins that row's chunk_root, shard_size, and added-at sequence in the challenge. The response proves possession against those pinned values; it does not re-prove live membership. This sampling and serialization change is re-genesis-only on the disposable network.

Recovery API

Paged reader and removal roots

Open Node #1724 adds GET /ras/chain/volumes/<id>/shards?after=&limit=&head_seq=. after is an exclusive ordinal; limit is clamped to 1–1,024. Each page returns entries, next_after, live_shard_count, current_head_seq, and the current manifest root. For this endpoint head_seq is an opaque inventory revision. Later pages require the first page's revision and return conflict after a manifest commit or GC row drain; the event API's sequence is separate. CBFS #265 has merged to devnet: volume_events.rs::read_chain_shards consumes these pages and restarts on conflict, while the SDK supplies exact nonzero roots for removed manifest-node and object shards. The earlier CBFS baseline emitted zero removal roots. A strict test of the merged CBFS callers against Node #1724, Node merge, coordinated deployment, and live import/restart proof remain rollout gates. Do not deploy the new CBFS reader against a Node without the paged route: recovery fails closed when it cannot establish the inventory. CBFS storage formats and the relay upload path remain intact.

Cleanup

No orphaned native rows

Normal removes delete their two rows immediately. After acknowledged event history is pruned, an independent bounded per-block GC lane rotates fairly among terminal volumes. Each item pops one last ordinal, deletes its primary row, decrements live_shard_count, and advances the inventory revision. A durable consensus cursor resumes after restart, while later rent epochs continue without duplicate settlement. The commitment remains while rows exist; the volume leaves the live index only after the count reaches zero. Terminal relay purge may precede native-row cleanup; nonterminal inventory rows still protect committed shards. The separate 1,024-event-per-epoch pruning cap remains a general CIP-10 liveness gap. A proposed follow-up needs a durable, fair per-block event-prune queue and deterministic admission backpressure on outstanding prune work: valid commits can create more work than the current sweep's shared 32-item-per-block ceiling. Stage ingress must reserve prune capacity so accepted staged commits are not blocked at finalize solely by prune saturation, and clients need automatic retry for temporary admission refusals. Permanently lost event-time relays need a separate safe ACK recovery or retirement path: eviction, assignment rotation, and terminal status do not clear the current signed-ACK prune gate. None of those follow-up behaviors is supplied by this native-inventory change, so this change alone does not establish indefinite production readiness.

Approved build scope

Build
  • domain-separated native SystemState inventory helpers in Node storage;
  • delta-only RAS commit validation and swap-delete/appends;
  • native-row-anchored challenge issue/read/verification using the existing response wire;
  • an independent bounded per-block native GC lane;
  • a paged Node inventory endpoint, the CBFS recovery reader, and real CBFS SDK removal roots;
  • focused transition, deletion, rollback, speculative execution, restart, PoR, pagination, 10,000-shard, and pending-108-ref tests;
  • a fresh disposable Homestead chain and workspace, followed by a clean archive import.
Do not build
  • per-page meta.json files;
  • a second Homestead registry or writer;
  • Homestead-side shard trees or proofs;
  • CBFS storage or relay-upload redesign;
  • a larger general actor-value cap;
  • a replacement for the service registry.

Acceptance gates

  1. Existing service-registry and room-snapshot tests remain unchanged and green.
  2. CBFS uses the same commit request schema and fields; removed shard references carry the exact nonzero root and size accepted by Node.
  3. A one-shard delta against a 10,000-shard volume touches a constant number of inventory rows and no single value contains the complete inventory.
  4. Removal validation through the CBFS caller seam, swap-delete integrity, zero-count and terminal-volume PoR exclusion in both samplers, relay byte accounting, volume events, fair per-block terminal cleanup beyond one epoch, crash resume, rent progress without duplicate settlement, paged pruned-cursor recovery, challenge-removal orderings, and native-row-anchored PoR have explicit passing coverage.
  5. The pending 108-ref commit and complete archive import finish without an actor-value-limit error.
  6. After the clean import, the service restarts from its CBFS journal/checkpoint and rerunning the importer creates no duplicate pages or assets.

  2. Build and deploy compatible Node and CBFS versions on dev-01. Keep the write-relayer, relay upload path, and relay image intact.
